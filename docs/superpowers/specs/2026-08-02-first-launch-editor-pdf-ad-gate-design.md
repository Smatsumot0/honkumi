# 初回起動・エディタ・PDF広告ゲート安定化設計

## 目的

アプリを新規インストール後に初めて起動した時でも、エディタの入力位置が跳ねず、広告処理とPDF生成が競合してカクつきやフリーズに見える状態を起こさないようにする。同時に、無料版では初回PDF出力を含む広告対象の出力でインタースティシャル広告を必須とする。

## 現状と原因

初回起動ログと現在のブランチを確認した結果、症状には次の独立した原因がある。

1. 前回のエディタ入力安定化修正が別ブランチにだけ存在し、現在のブランチには反映されていない。本文が自動フォーマットで変化していない入力でも独自のスクロール復元が実行され、`UITextView` の標準カーソル追従と競合する。
2. `Info.plist` の `UIAppFonts` に登録済みの13フォントを、`HonkumiApp.init` からCoreTextへもう一度同期登録している。初回起動のメインスレッド上で不要なファイル走査と登録失敗が発生する。
3. 起動直後の `prepareForAppLaunch()` が、UMP同意更新だけでなくGoogle Mobile Ads SDKの開始とインタースティシャル広告の読込まで行う。`PDFExportAdService` は `@MainActor` であるため、`Task(priority: .utility)` から呼び出してもメインアクターを離れない。新規シミュレータでは、広告関連WebKit処理が起動後約30秒間継続していた。
4. PDF生成そのものはバックグラウンドで実行されるが、初回の組版・フォント・PDFキャッシュが冷えた状態で広告WebKit処理と重なるため、CPUとメインスレッドの応答性が悪化する。

## 合意済みの広告要件

- Pro版では広告処理を行わない。
- 無料版では、初回PDF出力を含む広告対象の出力で広告表示を必須にする。
- オフラインまたは通信障害で広告を取得できない場合はPDF出力をブロックする。
- 広告リクエストが成功したものの広告在庫がない場合だけ、広告を表示せずPDF出力を許可する。
- 広告の表示準備または実際の表示に失敗した場合はPDF共有へ進めず、再試行可能なエラーを表示する。
- 既存の作品単位5分クールダウンは維持する。クールダウン中の出力は新しい広告表示を要求せず、そのままPDF出力を許可する。

Google Mobile Ads SDKのリクエストエラーでは、広告在庫なしの `RequestError.Code.noFill` と通信障害の `RequestError.Code.networkError` が区別される。このSDK固有判定はGoogleアダプター内に閉じ込め、アプリ本体へGoogle SDK型を漏らさない。

## 採用する処理順序

起動時の広告事前読込を廃止し、無料版の広告対象PDF出力を明示的なゲートとして扱う。

1. アプリ起動時はUMP同意情報の更新と、必要な同意フォーム表示だけを行う。
2. エディタ表示中はGoogle Mobile Ads SDKの開始、インタースティシャル広告読込、15秒間隔の自動再試行を行わない。
3. 無料版の利用者がPDF出力を開始した時、クールダウンと同意状態を確認する。
4. 広告が必要なら「広告を準備しています」と表示し、Mobile Ads SDKを一度だけ開始して広告を読み込む。
5. 広告読込結果が表示可能なら、広告を保持したままPDFを生成する。広告読込とPDF生成は同時に実行しない。
6. PDF生成成功後に広告を表示する。広告が閉じられた後だけ共有シートを表示する。
7. 広告在庫なしの場合はPDFを生成し、広告なしで共有シートを表示する。
8. 通信障害などのブロック対象エラーではPDF生成を開始せず、エラーを表示して出力操作を終了する。

広告の実表示をPDF生成成功後に置くことで、PDF生成失敗時に広告だけを表示する状態を避ける。広告読込はPDF生成前に完了させるため、初回の重い処理同士は競合しない。

## 広告ゲートの結果

広告サービスは「広告を表示したかどうか」だけでなく、PDF出力を続行できるかを型で返す。

- `ready`: 表示可能な広告を保持しており、PDF生成後に表示する。
- `notRequired`: Pro版、購入状態未確定、または作品単位クールダウン中で広告が不要。
- `noFill`: 広告在庫がないため、今回だけ広告なしで続行可能。
- `blocked`: 通信障害、タイムアウト、同意状態不備、設定不備、SDK内部エラーなどにより続行不可。

`noFill` はGoogle Mobile Adsのリクエストエラードメインと `RequestError.Code.noFill` の組合せだけを対象にする。不明なエラーを広告在庫なしとして扱わない。`networkError`、サーバーエラー、タイムアウト、不正リクエスト、アプリID・広告ユニットID不備はすべて `blocked` とする。

広告読込には15秒の上限を設ける。上限を超えた場合は通信状態を確認して再試行するよう案内し、バックグラウンドで自動再試行しない。利用者が再度PDF出力を実行した時だけ再試行する。

## UI状態

無料版のPDF出力は、一つの操作内で次の表示状態を遷移する。

- `広告を準備しています…`
- `PDFを生成しています…`
- インタースティシャル広告
- 共有シート

処理中はPDF出力操作の多重実行を拒否する。非同期処理中もメインスレッドを同期的に待たせず、進捗表示のアニメーションとキャンセル可能な画面更新を維持する。

ブロック対象エラーでは共有シートを開かず、次の内容を表示する。

- タイトル: `広告を読み込めませんでした`
- 本文: `通信環境を確認して、もう一度PDF出力をお試しください。`

広告在庫なしは利用者向けエラーを表示せず、そのままPDF生成へ進む。詳細なエラードメイン、コード、レスポンス情報は診断ログにだけ記録する。

## エディタ修正

`docs/superpowers/specs/2026-08-01-editor-input-scroll-stability-design.md` の承認済み修正を現在のブランチへ反映する。

- 自動フォーマット結果が入力直後の本文と同じ場合は、Bindingへの本文・選択範囲反映だけを行う。
- この経路では `contentOffset` を復元せず、独自のカーソル表示処理を呼ばない。
- 本文が実際に置換された場合だけ既存の選択範囲補正と表示調整を行う。
- 検索、章移動、最下部移動などの明示的なナビゲーションは変更しない。

## フォント登録

バンドルフォントの登録元を `Info.plist` の `UIAppFonts` に一本化する。

- `HonkumiApp.init` から `AppFontCatalog.registerBundledFonts()` を呼ばない。
- `UIAppFonts` に、`AppFontCatalog` が参照する全バンドルフォントファイルが含まれることをテストする。
- CoreTextのプロセス登録処理と登録済みファイルキャッシュは、他に利用箇所がなければ削除する。
- フォント名、選択肢、PDF埋込み、既存作品のフォント設定互換性は変更しない。

## 既存仕様との関係

本設計は、次の既存仕様の広告失敗時動作を無料版の広告対象出力に限って置き換える。

- `docs/superpowers/specs/2026-07-22-pdf-export-ad-boundary-design.md`
- `docs/superpowers/specs/2026-07-26-honkumi-preview-pdf-ad-reliability-design.md`

置き換えるのは「広告未準備・広告失敗時も直ちに共有する」「起動時に広告を事前読込する」という部分である。Google SDK型をサービス境界へ閉じ込める構成、PDF生成成功後に広告を実表示する順序、Pro版の広告なし、作品単位5分クールダウン、重複完了防止は維持する。

## テスト方針

### エディタ

- フォーマットで本文が変わらない通常入力はスクロール調整を要求しない。
- 自動フォーマットが有効でも本文が変わらなければスクロール調整を要求しない。
- 本文が実際に置換された場合だけスクロール調整を要求する。

### 起動とフォント

- 起動準備はUMP更新と必要なフォーム表示を行うが、Mobile Ads SDK開始と広告読込を行わない。
- `UIAppFonts` が `AppFontCatalog` の全バンドルフォントを含む。
- 新規シミュレータの初回起動ログに重複フォント登録エラーがない。

### 広告ゲート

- Pro版は広告ゲートを通さずPDFを生成・共有する。
- 無料版の初回出力は広告読込完了後にPDF生成を開始する。
- 広告読込成功時は、PDF生成成功後に広告を表示し、広告終了後に共有する。
- `noFill` の場合だけ広告なしでPDFを生成・共有する。
- `networkError` と読込タイムアウトではPDF生成・広告表示・共有を行わない。
- 不明な広告エラー、設定不備、広告表示失敗では共有を行わない。
- ブロック後に再実行すると、広告読込から再試行できる。
- 作品単位5分クールダウン中は広告読込を行わずPDFを共有する。
- 出力ボタン連打でも広告読込、PDF生成、広告表示、共有は一組だけ実行される。

### 実機相当の確認

- 新規iOS 26.5シミュレータで初回起動し、エディタ表示中にインタースティシャル広告由来の継続的なWebKit処理が始まらないことを確認する。
- 無料版の初回PDF出力で進捗表示が更新され、広告読込とPDF生成が直列で実行されることを確認する。
- ネットワーク無効時にPDF共有が開かず、再試行メッセージが表示されることを確認する。
- テスト広告の表示後に共有シートが一度だけ開くことを確認する。

## 完了条件

- 対象の回帰テストが失敗する状態を確認してから各修正を実装し、すべて成功する。
- Simulator向けDebugビルドが成功する。
- 新規シミュレータの初回起動で重複フォント登録がなく、広告本体のWebKit処理がエディタ操作開始前後に継続しない。
- 無料版の初回PDF出力では、広告表示成功または広告在庫なしの時だけ共有できる。
- オフライン・通信障害・広告表示失敗では共有できず、画面がフリーズせずに再試行できる。
